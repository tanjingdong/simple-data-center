项目定位与架构总览

更新时间:2026-09-09 | 适用版本:V0.7.x | 面向二次开发者

Simple Data Center 是一个生产级的 CRUD 应用基座:基于 PocketBase 与 React 构建,编译为单个可执行文件。它把二次开发所需的「基础设施」准备齐全——认证、用户体系、文件存储、反向代理、数据管理后台——业务开发只需要按标准模式添加自己的数据集合与页面,而不是重复建设底座。

定位:基座,而非单一应用

理解本项目的关键只有一句话:

  • 基座与业务的分界:凡属于「认证 / 账号 / 文件 / 网关 / 管理工具」范畴的能力归基座;凡属于具体业务语义的代码与数据归业务模块,二者在目录与数据归属上严格分开。
  • 业务的标准生长方式是「定义集合 → 服务函数 → 页面路由 → 入口」四步,详见「二、业务模块开发」。
  • 历史上曾内置示例业务模块(V0.7.2 起已移除),当前仓库即纯基座,可直接整体复制为二次开发起点。

项目价值与应用场景

「定位」回答了它是什么;这一节回答更实际的问题——什么情况下值得选它,而不是自己搭一套,或去买一个 SaaS。

一个典型的基层场景:把「台账」搬上浏览器

先从一段几乎每天都在发生的场景讲起(情节做了抽象,但它由无数真实需求拼成):某镇政府的应急管理办公室,每年要按上级要求完成数百次安全生产检查,并做到「检查有记录、隐患有闭环、年终可归档迎检」。办公室的老李是负责人(业务管理员)——他不懂代码,单位也没有专职 IT;各村网格员(业务使用者)平时用手机拍现场照片,回办公室再补 Excel;电脑都在单位内网,数据按纪律要求不能放进任何商业云盘。现实中的痛点环环相扣:

  • 上级要求留痕闭环,基层却靠 Excel 硬撑:文件在 U 盘和微信群之间传来传去,版本打架、字段乱填、照片与记录分离——迎检前全科室通宵补录是常态。
  • 没有 IT,也不许上云:数据涉密纪律与单位规定排除了商业云;区里统建的大平台又没有这个业务,基层只能自己想办法。
  • 市面系统不对路:要么按年招标、按人头报价;要么数据在厂商服务器上,流程要基层迁就系统——领导不放心,预算批不下来。
  • 自己攒,养不起:一个会写前后端、又会部署服务器的人,在基层是稀缺资源;外包报价高,交付还是黑盒,以后没人维护。
  • 表格与问卷只能「收」不能「管」:检查记录要持续更新、照片要归属到人、隐患要跟踪到关闭——这是表格范式的天花板。

转折在于:单位里那位「会点代码的同事」用这个基座花两天搭了一套「安全检查台账系统」——交付物是一个文件、一个数据目录、一页说明书。管理员老李在一台旧电脑上照说明书执行一次启动命令;没有公网 IP 也没关系,搭建者预先在管理工具里配好 frpc,老李在浏览器里点一下「启动」,全镇网格员就能通过一个网址登录使用。此后一切都发生在浏览器里:手机拍照直接上传(文件归属到人、权限按规则控制)、隐患状态按设定流转、年底一键导出归档;数据始终在单位自己的硬盘上;明年流程要改,代码就在仓库里,换谁都能接手。

这套设计真正的巧思,不在于某一项具体技术,而在于它把基层最稀缺的资源——「会运维的人」——从使用条件里删掉了,并且让链条上的每一环都只做自己会做的事。下面的分析,就是把这份巧思逐层拆开讲清楚。

关于这个名字:Simple Data Center

名字本身就是一句设计声明——三个词分别对应三层取舍:

  • Simple:简单是给使用者和运维者的,不是功能简单。认证、文件、反代、网关、管理后台一样不少;被简化掉的只是「运行它所需的成本」——一个文件、一条命令、一份数据目录。
  • Data:数据是主体,不是附属品。所有功能围绕「让数据被安全地录入、约束、流转与带走」展开;数据落在自己的磁盘上,格式开放、随时可迁。
  • Center:一层具体、一层抽象。具体的是登录后的数据大厅(/center)——各业务功能的统一入口,「中心」正是这个页面的名字;抽象的是定位——把你散落在 Excel、网盘、聊天记录里的业务,收拢到一个自主可控的中心站点上。

合起来读:一个以数据为中心、简单到能自己部署的站点。它不追求功能大而全,只追求「你需要的那部分,恰好都在,而且都听话」。

价值所在

  • 基础设施零重复:对 CRUD 类应用,注册/登录/找回密码、用户资料、管理后台、文件上传、对外暴露,这些是所有项目都要写、又毫无业务价值的样板。基座一次性做完并经过真实使用打磨,业务方只写集合与页面。
  • 单文件即产品:交付物是一个可执行文件 + 一个数据目录,运行环境随制品走(设计动机与使用者收益的完整分析见下节专述)。
  • 数据自主可控:数据落在本地 SQLite,文件落在自己接的 Alist 存储上,对外可见性由访问规则决定(匿名只能读 public)。适合对数据归属、隐私、离线可用有要求的场景。
  • 二次开发成本是「复制粘贴」级别:标准四步模式 + 现成模块做参照(README 与「二、业务模块开发」均以 filestore/files 为模板),同时它有一个更珍贵的特性——不是脚手架:认证、文件、反代等模块都从真实使用中演化而来(前身即为习惯追踪应用),边界、校验、报错文案是磨过的,不是 hello world。

价值的三层角色:开发者 → 业务管理员 → 业务使用者

上面的「价值所在」是从开发者视角说的——但这只是供给端。一个业务系统真正被采用,取决于链条末端的另外两类人。基座的价值不在于「帮开发者省了多少代码」,而在于每一层角色都能只做自己会做的事,把不会做的事交给上一层消化掉。

角色他们是谁 / 不会什么这套设计给他们的东西他们需要做的
开发者(技术提供方) 会写代码,负责把基座变成某个具体业务系统 四步模板 + 现成模块参照,交付物收敛为「一个文件 + 一个数据目录 + 一页说明书」 写业务页面与集合;按需配好 frpc / filestore 等内置工具
业务管理员(组织内的拍板与维护人) 不懂代码、不懂开发、不懂部署、没有专门服务器,最多能照说明书执行一条命令 上线门槛 = 把文件放到任意一台常开设备(旧电脑 / NAS / 最便宜的小主机),照说明书执行一次;此后账号、参数、基础数据都在浏览器里维护;备份 = 定期拷贝数据目录;升级 = 用新文件替换 按说明书启动一次;日常打开管理后台维护;定时拷目录做备份
业务使用者(员工 / 终端用户) 不懂也不关心技术,只关心业务本身 一个网址、一个账号:数据以「业务视图」呈现,该填什么、谁能看、怎么流转,全部由系统按设定固化,不需要人肉约定 打开浏览器,登录,按流程操作数据
[开发者] 写业务(集合/页面/服务),交付单文件+数据目录+说明书 │ 消化:开发复杂度 ▼ [业务管理员] 照说明书启动一次,此后全在浏览器里管理 │ 消化:部署与运维复杂度(无运行时/无数据库/无多组件) ▼ [业务使用者] 打开网址 → 登录 → 按固化工作流操作数据 │ 消化:操作复杂度(数据约束与权限由系统保证)

组织里真正为系统「买单」的,往往不是程序员,而是业务管理员。他评估一件事的标准从来不是技术选型,而是三个问题:

  • 要多久才能用上?——基座路径下,开发者交付后,他照说明书跑一次命令即可上线,而不是等采购、等部署、等外包排期;
  • 数据在谁手里、长期要花多少钱?——一次性的开发成本,数据始终是本地文件,没有按席位/按记录数的持续账单,也没有「平台涨价/停服」的被动;
  • 以后想改,找谁?——代码在仓库里、MIT 许可,可以换任何开发者接手,不被单一厂商或平台绑架。

而业务使用者的体验,决定这套系统是否被真正用起来:一个普通员工(比如报销、设备申领、登记台账)只需要登录、填单、上传附件、看到状态流转;他看不到「后端」「数据库」「部署」这些词,也不需要知道——这正是前面所有设计(单文件、同源、SQLite、内置工具)的最终落脚点:让最末端的人无感,让中间的管理者不慌,让最前端的开发者不累。

为什么坚持「单文件 + 打包前后端 + SQLite」

这三个决定看起来是技术取舍,本质上是在回答同一个问题:「最终会部署它的人,是谁?」答案通常是个人、小团队、内部管理员——没有专职运维的人。于是设计目标随之确定:让交付物自己携带全部运行条件,使用者的部署公式被压缩到只剩「放在哪、运行哪个文件、数据目录指到哪」。

  • 单文件:运行环境随制品走。把「运行环境」从部署公式中删掉,使用者不需要装 Node、Go,不需要静态服务器与进程管理器。收益全在终端一侧:
    • 一个文件就是一个产品:心智模型、部署文档、故障排查对象都只有一个。
    • 升级与回滚都是「换一个文件」:旧文件留着就是回滚方案,没有多组件版本配对问题。
    • 分发 = 复制:U 盘、网盘、scp 拷走即用,离线与内网环境同样成立。
    • 排查面最小:只有一个进程、一个日志文件要看。
  • 前后端打包(embed):消灭「两个地址」。单文件是形态,同源才是目的——页面与 API 来自同一端口,于是:
    • 无需任何反代与跨域配置:没有 CORS、没有 /api 转发、没有多域名证书;对使用者来说,「网址」只有一个。
    • 登录态天然顺畅:同源 cookie 直接生效,不需要为跨域鉴权做任何额外设计。
    • 暴露面收敛为一个端口:防火墙、内网穿透都只针对 8090——这正是 frpc 工具默认 frpc_local_port = 8090 的原因。
    • 页面与接口永远同版本:不存在「前端升了、后端没升」的错位组合,发布即原子操作。
  • SQLite:把「数据库服务器」从架构中删掉。数据只是一个文件,这带来使用者最能直接感知的几件事:
    • 备份 = 拷贝文件,恢复 = 放回文件:不需要了解任何数据库运维,灾难恢复是普通人都能执行的两步操作。
    • 搬家与换机 = 整个数据目录拷走:换机器、甚至换操作系统,数据原样跟上。
    • 没有常驻数据库服务:无守护进程、无端口、无数据库账号,资源占用低,树莓派 / NAS / 旧小主机都能安静运行。
    • 文件格式开放而长寿:SQLite 文件可迁移、可只读检查、无厂商锁定——对「打算用很多年」的个人与组织数字档案,这点尤其重要。
    • 一个实例 = 一个数据目录:模型简单到不可能出现「多个进程抢同一个库」的部署错误。

把三者合起来看,本质是一句话:交付复杂度守恒——所有复杂都被作者预付在构建期,而不是转嫁给使用者在运行期支付。最终使用者不需要「会部署」,只需要「会拷贝文件」;而它的边界也同样清晰:这些收益以单机规模为前提,一旦业务需要多实例共享同一份数据或高并发写入,就该考虑换架构了(见下节「什么时候不该选它」)。

典型应用场景

场景形态为什么是它
个人数据自管理习惯打卡、健康/运动记录、记账、读书摘录等单人应用数据不想交给云厂商;单文件可放在自己的 NAS/电脑/小主机上;前身 Long Habit 即验证过这条路径。
团队内部工具设备/资产台账、值班排班、客户登记、订单跟单、报销单等「几张表」系统买 SaaS 太重、数据在别人手里;内部人维护一个基座应用,比维护一套前后端脚手架省事得多。
垂直小产品 MVP独立开发者快速验证一个领域工具账号、后台、文件、公网访问全部就绪,可先交付真用户,验证成立后再重写也不可惜——因为业务代码本来就只占一小部分。
自托管 / NAS 用户网页文件管理 + 给家人朋友开账号 + 内网服务外露filestore 对接 Alist 覆盖文件能力,frpc 一键暴露到公网或子网,免去维护隧道与反代。

教学与快速定制交付全栈教学样例、外包交付的内部管理系统一套现代前端 + Go 后端的真实代码库,带测试与单文件产物,交付与讲解都轻。

与常见替代方案的对比

「做几张表的业务系统」这件事,市面上已有从零代码到自研的整条光谱。本节把最常被拿来比较的方案摊开,看各自的天花板在哪,以及换到本基座后,使用者原先的痛点分别落在哪里。

常见方案它的定位(能做什么)天花板(通常卡在哪)与基座的解法
单机 Excel / WPS 零成本、人人会用的二维表 没有身份与行级权限,单文件随手改坏,无法网页/移动访问,字段无类型与枚举守门。基座把它升级成「有账号、有约束、有页面」的表,而备份仍然是拷目录。
Excel + 网盘共享 解决跨设备与多人轮流编辑 「同步冲突 / 双开覆盖」是文件模型的死结;谁都能改、无审计;把文件外链给外部人不安全。基座只有一份数据,一个事实源,访问由账号与规则控制。
在线表格 / 多维表格(腾讯文档、金山、Sheets、飞书多维表格等) 实时协作、门槛低、生态广 仍是「表格范式」:数据约束弱(格式随手破坏),权限粒度粗,想做成「像样的产品界面」(录入表单、详情页、附件归属、状态流转)得跟平台范式较劲;数据出口握在别人手里。基座的界面是真正的 React 页面,规则由后端强制。
低代码 SaaS(简道云、明道云、钉钉宜搭、Airtable 等) 可视化建模、模板多、上线最快 按席位/用量计费,平台升级与停服不受控;超过模板时要去搏平台的表达式与脚本;数据迁移永远是最痛的一步。基座是 MIT + 全代码在仓库 + 数据永远是文件,代价是业务页面自己写(四步复制模板即可)。
自托管低代码(NocoDB、Baserow、Budibase 等) 开源、数据在自己手里 「自托管」不等于「轻运维」:多数要数据库 + 多进程/多容器,升级与备份并不比自研省心。基座把运维复杂度一并打进单文件,才是真正意义上的低运维。
在线表单问卷(腾讯问卷、金数据、Microsoft Forms 等) 收集即所得,统计图表友好 定位是「收」不是「管」:填完即断,没有登录态、没有「改自己的历史记录」、没有状态流转与附件归属。基座的表单背后是持续可管理的业务数据。

还有一类常被拉来比较、但并未真正同场竞争的对象:老牌桌面数据库(Access、FileMaker——Web 化与跨平台是硬伤)、企业网盘全家桶(Nextcloud 等——文件能力强、表格与应用弱、部署更重)、垂直 SaaS(业务不在其模型内只能将就)、以及「自己搭一套前后端脚手架」(把基础设施与技术债一并留给自己养,恰是本基座要消除的部分)。它们的共同分界线只有一条:要么把数据锁在平台里,要么把运维留给你,要么把开发量留给你——本基座选择把三者都从使用者身上拿走,只留下一份可以永远带走的代码与数据。

因此比较优势可以收敛为三点:

  • 对表格类:补上身份、约束与页面——「像表格一样简单,像数据库一样可靠」;
  • 对低代码类:解除锁定——代码在仓库、数据是文件、付费与停服都与你无关;
  • 对自托管类:把运维打进单文件——交付门槛回到「拷一个文件」。

这也划出了它真正的受众分界线:表格与低代码卖给「不想碰代码的人」;这个基座卖给「不想碰基础设施、但愿意维护一个仓库的人」——它不承诺人人可用,只承诺:只要你愿意改前端,其余全部替你扛。

什么时候不该选它

  • 重协作 / 实时类(多人同时编辑同一文档、聊天、白板):需要实时同步与冲突处理,SQLite 单机 + CRUD 模型不是为此设计。
  • 复杂企业治理:没有租户隔离、细粒度 RBAC 与审批流;访问控制是「集合规则」模型,适合内部工具级权限。
  • 重型处理流水线:图片/视频转码、大数据分析等重活应放在外部服务,由业务自行编排,基座不做也不该做。

一句话判断法:当你的业务本质是「若干张表 + 账号 + 文件 + 需要被内网/外网访问」时,这个基座已经替你做完了其中约八成的工作——剩下的两成,正是最有业务价值的部分。

总体架构

三条决定整个项目形态的架构决策:

  • 单文件部署:前端构建产物通过 Go embed 打入二进制,产物只有一个可执行文件,静态资源、API、数据层同进程。
  • PocketBase 是框架,不是独立进程:它以 Go 包形式被本工程引用,因此可直接使用其 Hooks、路由绑定、中间件、数据库、邮件、日志等全部扩展点(接入写法见「二、业务模块开发 → 后端」)。
  • frp 以 Go 库嵌入:frp 客户端(frp v0.70.1)以库形式内嵌,不引入外部进程,维持跨平台单文件(见「三、内置模块与扩展接口」)。
[前端 dist/ 产物]──embed──▶ 单二进制(Go 主进程) ├─ PocketBase 扩展(集合 / API / 认证 / Hooks) ├─ 基座功能包(auth、filestore、frpc、links…) └─ SQLite 数据文件(位于启动目录,相对路径!)

开发模式(前后端分跑 + 热重载)与生产模式(单文件)行为等价;两者差异与踩坑点见「一、概览与开发环境 → 本地开发与常用命令」。

本节回答一个最实际的问题:「这段代码应该放哪里」。全项目只有两个代码源——backend/(Go)与 frontend/src/(React);其余目录都是产物、数据或过程文档。

hooks/、context/、types/use-auth / use-settings / use-throttle;全局上下文;PocketBase 生成类型与通用类型。

「放哪里」决策规则

  • 纯 CRUD 业务:集合 → services/api-*.ts → pages/ 页面 → router.tsx 注册 → 大厅入口;无需改任何 Go 代码。
  • 需要后端参与的定制:backend/ 根目录一个接线 .go + 自建独立目录包;不要把业务语义写进基座包。
  • 通用 UI 与工具函数:放 components/shared 或 lib;仅供单页使用的组件就近放在该页面目录。
  • 规则类校验:前端 schemas/ 与后端集合规则同构,改动需两端一起做(详见「二、业务模块开发」)。

本地开发与常用命令

环境要求

  • Go 1.26+、Node.js 25+(或 Bun 1.3+);Docker 可选,仅容器部署需要。

一键开发 vs 分拆启动

npm run dev:client # Vite 热重载开发服务器 npm run dev:server # cd backend && go run . --dir=../db serve(默认 8090)
  • 端口与代理:Vite 把 /api 代理到 VITE_BACKEND_URL(默认 http://localhost:8090);前端 services/pocketbase.ts 使用相对路径实例化客户端,开发与生产均同源访问,无需硬编码域名。

首次初始化

  1. 创建管理员:任选一个可执行入口执行 superuser upsert——生产二进制为 ./simple-data-center superuser upsert 邮箱 密码;开发时等价于 cd backend && go run . --dir=../db superuser upsert 邮箱 密码(参数写法与 serve 一致)。

数据目录由 --dir 决定且按启动目录解析——请固定从同一目录启动服务,否则会出现「数据全空、登录报错」的空库现象,详见「四、部署与项目治理 → 常见问题」。

开发态与生产态的差异

  • 生产二进制带 production tag,经 fs-prod.go 将 backend/dist 用 embed 打入;开发态(fs-dev.go)由 Vite 提供静态资源。
  • 只改前端代码时 npm run dev 即可热重载,不必每次重编 Go;改 Go 代码或做最终验证时再执行 npm run build。
  • 仅修改管理配置(如 links_*)无需重启即生效;frpc 配置修改后需在工具页「重启」才生效——两者规则不同,注意区分。

规范与注意事项

  • 代码、注释、文档一律中文;前端用户可见文案亦为中文。
  • npm run lint 是 build:client 的前置步骤,提交前必须通过;顺手执行 npm run pretty 统一格式。
  • 新增/修改集合后,须同步导出回 backend/pb_schema.json,保持仓库声明与运行库一致。
  • 网络受限(npm registry、Go proxy 不可达等)时按项目约定「只报告、不绕过」——不要私自换源或挂代理。

开发模式总览

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

基座定义了一条业务开发的标准路径——定义集合 → 服务函数 → 页面路由 → 入口。本组五篇文章即按此展开;开始之前,先记住两条判断规则:

  • 纯 CRUD 业务不需要写任何 Go 代码:数据存储、权限、校验、API 全部由 PocketBase 提供,你只写前端与集合定义。
  • 只有「网关型 / 代理型 / 后台任务」才需要后端代码:这类需求在 backend/ 自建独立目录包接入,不得改动基座包语义。

2. 服务函数api-xxx.ts 增删改查封装frontend/src/services/
3. 页面路由页面组件 + 路由注册frontend/src/pages/ + router.tsx

参照物

不要从零发明结构。仓库里有一个完整的横向切片可照抄——文件存储(/files):它的集合(filestore_files)、服务层(api-filestore.ts)、页面(pages/files/)、路由(filesRoute)、大厅入口(business-modules.ts)五处齐全,是「四步」最标准的范例。需要更复杂的后端形态时,参看 links(最小网关:配置 + 公开路由)与 filestore(代理 + 流式转发)。

约定:业务模块的代码目录自包含(页面、组件、服务同域归拢),避免散落到全局目录;基座只认「注册表」中的入口,不感知业务内部结构。

后端:集合与框架接线

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

后端只有两件事需要你关心:数据长什么样(集合),以及定制逻辑挂在哪里(接线)。

PocketBase 作为框架

PocketBase 不是独立进程,而是被本工程以 Go 包引用(backend/main.go 中 pocketbase.NewWithConfig)。启动序列决定了各基座模块的挂载时机:

main.go: newApplication → mountFs(静态资源) → 邮件模板 → auth hooks → frpc.NewManager + setupFrpc → setupFilestore → setupLinks → pb.Start()

每个 setupXxx 都是同一个套路:在 OnServe 钩子里幂等补插默认配置项,再 RegisterHandlers(e) 挂路由。新增后端功能时照此模式写。

集合与 schema

  • 单一事实源是 backend/pb_schema.json:集合在管理后台 /_/ 创建/修改后,必须导回该文件并提交;新环境靠 Settings → Import collections 导入。
  • 当前集合:users、settings(用户偏好)、tools_settings(系统配置)、filestore_files(文件登记)等;前两者和 filestore_files 都有配套代码依赖其字段名,改字段前先全局搜索引用。
  • API Rules 在集合上配置,是真正的安全边界:公开只读、登录可读、仅创建者可改等都在这里表达;前端守卫只是体验层(见「入口注册与访问控制」)。

定制逻辑挂哪里

需求落点与参照
集合记录的生命周期钩子(如创建用户时补建 settings)backend/ 根目录的接线文件,OnModelAfterCreateSuccess 等;参照 auth.go
新 API / 网关路由(含鉴权)自建 backend/xxx/ 包 + backend/xxx.go 接线;包内 RegisterHandlers 注册,参照 links/
超级管理员专属接口handler 内 re.HasSuperuserAuth() 判权,参照 links/handler.go
流式转发 / 大响应(文件类)参照 backend/filestore/handler.go(代理模式)

边界:业务语义不要写进 filestore/frpc/links 这些基座包;基座包只服务各自工具,业务代码自建目录。

前端:页面、路由与服务层

几条本项目特有的规矩

  • 客户端用相对路径:new PocketBase() 不带域名,开发态由 Vite 代理 /api,生产态同源——不要硬编码后端地址。
  • 数据在渲染前就绪:路由 loader 里用 queryClient.ensureQueryData 预取(参考根路由),页面内用 TanStack Query 读缓存,不要在 useEffect 里手抓数据。

入口注册与访问控制

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

页面写完只是「能访问」,把入口挂进大厅/管理工具才算「能到达」。两处注册表是唯一的入口事实源:

入口注册表注意
数据大厅(/center)业务卡片lib/business-modules.tspath 是字面量联合类型——新增路由后需同步扩展类型,否则编译不过(这是刻意设计,确保卡片不会指向不存在的路由)
管理工具(/admin)工具卡片pages/admin/admin-tools.ts注册表驱动卡片渲染;但路由是显式声明的(router.tsx 的 adminToolRoutes 需手加一行)——用 map 动态生成会丢失字面量类型,注释里写明了原因

访问控制三层

按「体验层 → 安全层 → 管理端」理解,改权限时先想清楚属于哪一层:

  • 路由守卫(体验层):lib/route-guards.ts 的 requireVerifiedUser('模块名') 一行接入,未登录/未验证即跳登录页。它只管跳转体验,不是安全边界。
  • 集合 API Rules(安全层):真正拦住非法请求的地方。业务数据落库前先问:匿名能读吗?他人能改吗?答案写进集合规则,而不是前端判断。
  • 管理端(superuser):/admin 不自己实现登录,未认证时整页跳 PocketBase Dashboard(/_/)登录,同一会话生效;工具 API 在后端 HasSuperuserAuth() 二次校验。
  • 匿名可见的公开入口(如 /links/help-center)是特例:路由不挂守卫,安全性由服务端网关自身保证。

新增模块的自检

  • 集合规则:默认最严,逐条放宽并说明理由;
  • 路由守卫:除公开入口外,一律挂 requireVerifiedUser;
  • 管理类接口:后端必须有 HasSuperuserAuth(),不能只靠前端隐藏按钮;
  • 文件名/浏览器直链可绕过任何前端判断——凡是「不想让无权者拿到」的内容,都要经后端校验。

  • 数据:集合改动已导出回 backend/pb_schema.json;新字段对旧数据的影响已考虑(默认值、是否可空)。
  • 安全:新集合的 API Rules 已配置;新管理接口有后端判权;不向前端暴露不该公开的配置(参照 links 的做法:配置 API 仅 superuser 可读)。
  • 文档:README 快速上手是否需要更新;CHANGELOG.md 按既有格式追加一条(用户可见变更必须记录);本手册相关章节若因改动而过时,同步修订。
  • 实机验证:开发模式跑通「注册/登录 → 进入大厅 → 打开新模块 → 增删改查」全链路;涉及 frpc/filestore 时,以生产二进制形态再验证一次。

排查顺序约定:实机问题先查环境、操作、数据,而不是直接改代码(端口占用、启动目录、集合未导入是三类高频原因,详见 FAQ)。

系统配置的存储与读取

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

所有管理工具类配置(不是业务数据)统一存放在 tools_settings 集合,字段为 option / description / type / value,按 前缀_名称 命名。你新增一个系统级配置项时,照下面三步走。

存储与补插机制

  • 幂等补插:每个功能模块在自己的 setupXxx 里,于 OnServe 钩子中补插缺失的默认值(见 backend/frpc.go / filestore.go / links.go 中的 ensureXxxSettings)。已存在的项不会被覆盖,可放心随版本新增字段。
  • 补插失败只告警不崩溃——最常见原因是 tools_settings 尚未导入,启动日志会给出中文提示。
  • 对客户端关闭:该集合不对普通 API 开放;需要展示配置的模块,由后端提供 superuser 专属的配置 API(GET/POST /api/xxx/config),前端只调它,绝不直读集合。

现有配置项一览

前缀模块说明
frpc_*反向代理server_addr / token / proxy_name / local_port / remote_port 等
filestore_*文件存储alist_url / token / 大小与 MIME 限制 / 下载模式 / 存储路径 / 两种占位图
links_*链接管理help_center_url / error_html

新增配置项要动的地方

  1. 后端:在对应 defaultXxxSettings 列表追加一条(option/description/type/默认值);
  2. 读取:模块的 LoadConfig 里把该 option 映射进配置结构体(容错读取,容忍空值);
  3. 写入:保存接口采用部分更新语义——只写请求中实际提交的项,未携带的保持库中原值(避免「只想改 A 却清空 B」);
  4. 校验:保存时后端二次校验;若前端也有表单,schemas/ 写镜像规则与同款中文报错(参照 links 的 URL 校验)。

文件存储 filestore(接 Alist)

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

定位一句话:本项目不写存储驱动——Alist 负责存文件,本项目负责鉴权、编排与元数据登记。filestore_files 集合是文件的登记簿,Alist 是字节仓库,两者只由本应用后端写入(禁止手改 Alist 后台,否则产生孤儿文件)。

三条链路

  • 上传:浏览器 → 后端(鉴权 + 大小/MIME 校验)→ 流式转发 → Alist,归档路径 {根路径}/{年}/{月}/{用户ID}/{uuid}.{ext}。
  • 下载:由全局配置 filestore_download_mode 决定——direct 签发 Alist sign 直链 302 重定向;或 proxy 由后端流式透传(不暴露 Alist 地址)。
  • 内联预览:下载 URL 加 ?inline=1,proxy 模式返回 Content-Disposition: inline,可直接用于 <img>/<iframe>;direct 模式该参数被忽略。

关键文件:backend/filestore/(alist 客户端 / config / handler 与全部单测)、frontend/src/services/api-filestore.ts(服务层,含 getDownloadUrl/getPreviewUrl/getAbsoluteFileUrl 等工具)、frontend/src/pages/files/(用户界面)、frontend/src/pages/admin/filestore-tool.tsx(管理配置与对账)。

业务模块如何使用

  • 不重复造轮子:业务表只需存一个 filestore_files 记录 ID(或 ID 列表)作为外键,上传/下载/删除全部调 filestore 提供的接口,不自行拼 Alist 地址。
  • 私有文件用原生 <img> 标签无法内联(标签不带鉴权头,会回退占位图),公开文件可直接内联——需要私有内联流时,参考现有 sign 思路扩展短期预览直链。
  • AI/外部系统读取文件时,直接给 filestore_files 记录的 REST API 地址(公开文件)或通过本项目代理接口(私有文件)。

链接管理网关与静态页发布

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

这是基座里最小的一个完整模块,适合作为「新增后端功能」的样板;它同时解决一个具体问题:导航栏「帮助中心」这类外链入口,目标是运行期可改的管理员配置,且配置内容不能泄露给任何人。

工作原理

  • 固定公开入口 /links/help-center(新标签页、匿名可见),后端每次请求实时裁决:合法 → 302(带 no-store)/ 未配置·非法 → 200 报错页;读配置失败(如集合未导入)也落报错页,不让公开页 500。
  • 校验规则:绝对地址(危险协议 javascript:/data:/vbscript:/file: 黑名单拒绝)或 / 开头的根相对路径;裸相对(如 help.html)基准未定义、一律拒绝并提示正确写法。
  • 前端零判断:导航栏只放一个静态链接,没有公开配置 API,非管理员永远读不到配置内容。脏数据也在网关处被拦下,到不了用户浏览器。
  • 报错页内容由管理员配置(links_error_html,支持任意 HTML 片段);留空用内置默认文案。

落点:backend/links/(config 校验 / handler 网关 / 单测)、backend/links.go(接线 + 默认配置补插)、frontend/src/services/api-links.ts、frontend/src/pages/admin/links-tool.tsx、frontend/src/schemas/links-schema.ts(镜像校验)。

静态页发布(帮助中心内容怎么放)

本项目的实践是「单文件 HTML + 内联 CSS/JS/图片(base64)」,零依赖、零构建,可直接浏览与秒级部署。本手册自身即此类产物,发布路径任选:

  • 丢到任意静态托管(内网 Nginx、对象存储),把 links_help_center_url 配成其绝对地址;
  • 或存入 filestore 的 public 文件,配置成其浏览链接(根相对或绝对均可)。

扩展第二、第三个链接

把 links 当作模板:新增 links_docs_url 之类的 option 到默认列表 → Config 结构体加字段 → handler 加一条网关路由 → 导航栏加一个静态入口。注意各链接独立裁决、独立报错,互不影响。

frpc、邮件与其余内置件

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

frpc(反向代理)

  • frp 客户端以 Go 库嵌入(backend/frpc/,frp v0.70.1),保持单二进制与跨平台编译;当前仅支持 tcp 单代理。
  • 管理工具页(/admin/frpc)提供启动/停止/重启、连接配置表单、状态展示;配置存于 frpc_* 设置项,改配置后需点「重启」才生效。
  • 设计上服务重启后 frpc 不自动启动,须管理员手动开启——这是安全默认值(frp 即公网暴露),不要在业务改动中打破它。

邮件

  • 基座内置三个场景:邮箱验证、密码重置、新设备登录提醒;由 PocketBase 邮件体系 + 自定义钩子驱动(backend/mailer.go)。
  • 模板是 HTML 文件,位于 backend/templates/(如 base.layout.gohtml),启动时加载;自定义外观直接改模板。

用户设置与账号体系(概述)

  • users 集合承载账号;用户创建时由钩子自动补建 settings 记录(主题、提醒偏好等),见 backend/auth.go。
  • 用户设置页(/user-setting)覆盖:头像、昵称、用户名、邮箱(含邮件确认流程)、邮箱可见性开关、修改密码;扩展账号字段时,前后端 schema 与表单需同步。

日志与运行文件

  • 日志配置在 backend/logger.go;健康检查路由的噪音日志已被刻意静音,排查时不要误以为缺日志。
  • 生产运行文件:server.log(已 gitignore)、数据目录、二进制本体——备份与排障范围就是这三者。

构建与发布

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

构建流程

npm run build ├─ build:client: lint → vite build(产物输出 backend/dist) └─ build:server: cd backend && CGO_ENABLED=0 go build -tags production → 根目录 simple-data-center
  • production tag 决定静态资源走 embed(fs-prod.go),这就是「单文件」的来源;CGO_ENABLED=0 保证静态链接,产物可直接丢进 Alpine 运行。
  • 日常发布推荐用菜单式脚本 dev_tools/build.sh:交互选择系统与架构,自动读取 package.json 版本号,产物同时落到 release/simple-data-center-{os}-{arch}-{版本}[.exe](归档)与项目根目录(运行)。它每次都会先重建前端,避免嵌入陈旧产物导致新页面 404。

版本与归档约定

  • 版本号源自 package.json;每次对外发布在 CHANGELOG.md 顶部追加版本条目(格式参照现有条目:分模块列要点,写明用户可见变化)。
  • release/ 保留历史产物用于回滚;发布产物命名必须带 os/arch/版本三段。

Docker

  • 多阶段 Dockerfile:Bun 构建前端 → Go 构建二进制 → Alpine 运行(serve --http=0.0.0.0:8090),约 20MB 级镜像。
  • docker-compose 暴露 8090,数据卷挂载 db 目录(Dokploy 场景用 ../files/db);自带 healthcheck 打 /api/health。
  • 注意 compose 中的服务名/容器名仍是上游遗留的 longhabit,fork 后按需改名。

数据、升级与备份

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

数据位置:先记住这个陷阱

数据目录由 --dir(或 DB_DIR 环境变量)决定,按启动时的工作目录解析相对路径。从不同目录启动同一个二进制,会各自创建一套空数据库——表现为「数据全空、登录报错」。运维第一原则:固定启动目录,或干脆用绝对路径。

  • 开发态:--dir=../db,即仓库根 db/。
  • 部署态:常规是二进制同级的 db/;容器内为挂载卷(compose 中 /app/db)。

备份与恢复

  • 数据库是全部业务事实源:备份 = 拷贝 db 目录(SQLite 主文件 + wal/shm);恢复 = 停服、放回目录、启动。建议低峰期或先停服再拷,避免拷贝到写入中的中间态。
  • 业务文件不在 db 里——它们在 Alist 侧,备份责任随之转移:确保 Alist 自身的存储有备份策略,本应用只登记元数据。
  • 第三方配置(邮件 SMTP、OAuth 凭据)在 PocketBase Settings 中,存于同一数据库,随 db 一起备份。

升级步骤

  1. 备份 db 目录(回滚的唯一保险);
  2. 替换二进制(或拉新镜像)重启;
  3. 若新版本含 schema 变更,按 CHANGELOG 的说明在 /_/ 导入最新 pb_schema.json 或执行增量字段添加;
  4. 回归验证:登录 → 大厅 → 各工具模块;frpc 若在用,记得手动重新启动。

日志

运行日志写 server.log(已 gitignore)。排查顺序:先看启动时的中文告警(常见为集合未导入、配置补插失败),再看各工具页的状态显示。发布前无需清理日志文件,但长期运行建议配置轮转或定期归档。

常见问题(FAQ)

更新时间:2026-09-10 | 适用版本:V0.7.x | 面向二次开发者

按「先环境、先数据」的排查原则排列,多数问题不需要改代码。

登录报错 / 数据全空

  • 现象:原本正常的账号登录失败,或进去后集合/数据都不见了。
  • 原因:几乎总是启动目录不对——数据目录按启动工作目录解析,从别处启动会新建空库。
  • 处理:确认启动目录固定(或改用绝对路径 --dir / DB_DIR),并在正确目录下找到原有 db。

「帮助中心」点开是报错页

  • 这是正常设计:links_help_center_url 未配置或非法时,网关展示报错页。
  • 处理:管理员到「管理工具 → 链接管理」填写合法地址(绝对地址或以 / 开头);裸相对路径会被拒绝,页面有中文提示。

filestore 链接打不开 / 图片不显示

  • 先查「连通性自检」:Alist 地址与 token 是否有效、Alist 是否可达。
  • 内联预览不生效:确认当前是 proxy 模式且 URL 带 ?inline=1;direct 模式下由 Alist 决定,参数被忽略。
  • 私有文件在 <img> 中显示占位图是预期行为(无鉴权头);如需私有内联,见 filestore 章节的扩展建议。
  • 上传失败:检查大小是否超 filestore_max_size、MIME 是否在 filestore_allowed_mimes 白名单内。

配置项补插失败 / 工具页异常

  • 启动日志若有「配置项补插失败」告警:先在 /_/ 导入 backend/pb_schema.json(含 tools_settings、filestore_files),再重启。
  • frpc 状态一直失败:核对地址可达性、token、proxy_name 唯一性;改过配置需点「重启」才生效。

开发态正常、生产态异常

  • 新页面 404:生产用的是 embed 进二进制的旧前端产物——重新 npm run build。
  • 接口地址错乱:检查是否硬编码了后端地址;客户端应始终用相对路径(见前端章节)。
  • 日志缺健康检查记录:属刻意静音,不是异常。
